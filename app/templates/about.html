About DVAA

A DVWA-shaped teaching lab for the OWASP Top 10 for LLM Applications 2026.

This application is deliberately vulnerable. It contains working prompt injection, data exfiltration, unsafe deserialization, SQL injection and cross-site scripting — on purpose. Run it on loopback, in the provided container, and never on a network you share.

Medium and High are meant to be beatable. Each ships a defense that looks reasonable and fails for a specific reason the OWASP text calls out. You are told what the defense is — that is part of the scenario, and in a real assessment you would read the code too. You are not told where it breaks, and that write-up is not hidden somewhere in the page for you to peek at either; it appears only once you have captured the level. If you are stuck for good, the weakness of every level is documented in that challenge's own challenge.py, which is where a security person would look anyway.

Impossible has a flag and no intended way to reach it. When a defense is built correctly the capability is gone rather than filtered, so the payload that beat High returns nothing at all. Capturing an Impossible flag is worth 100 points because it does not mean you solved the challenge — it means you found a hole in the lab that nobody planted. Please report it.

Surrogate challenges

Three risks in the 2026 list are train-time or distribution-time: you cannot honestly exploit them inside a web app without actually training or shipping a model. Rather than fake it, those challenges are built as clearly-labelled surrogate scenarios that reproduce the mechanism at runtime — a dependency resolver picking the wrong artifact out of a registry, a feedback loop that poisons a store across sessions. The challenge page says exactly what is real and what is stood in for.

Where your progress lives

Captured flags are rows in the lab database, keyed by the session id in your browser cookie. Losing either one loses your progress, and from the hub the two look identical — so both are printed here. Write the session id down if you care about a long run; you can paste it back below to pick the run up again from another browser, or after a cookie has gone missing.

solves recorded {{ lab.solves_here }} on this session, {{ lab.solves_total }} in the database {% if lab.solves_total > lab.solves_here %} — an earlier session's solves are still in there. {% endif %}

In Docker, both the database and the salt live in the dvaa-data volume. docker compose down keeps it; docker compose down -v deletes it and starts the lab over.

Provider

Currently running on {{ provider_label }}. DVAA ships with a local Ollama default so nothing here costs money — which matters, because LLM06 is a genuine denial-of-wallet challenge. Point it at a metered API and a learner doing their job properly will run up a real bill.

Small local models follow system prompts loosely. If a High-level defense seems to collapse for no reason, that is often the model being weak rather than your payload being good. The reverse happens too: a 3B model can lose the thread of a multi-step tool-calling loop and stall on a challenge it should walk through, which reads as a broken lab and is not. The picker in the header switches between the models this Ollama has pulled — reach for it before you conclude a challenge is broken.
